# 0034. フォントの処理を 1 つのロックで守り、別のスレッドで Bitmap に文字も描けるようにする

- 状態: 承認
- 日付: 2026-10-04

## 背景

[ADR 0032](0032-canvas-api.md) の③。重い描画を別のスレッドで Bitmap に描き([ADR 0033](0033-bitmap-paint-box-and-layers.md))、
Task([ADR 0029](0029-threads-and-post.md))で Image として返したい。図形と画素は Bitmap ごとに独立しているので別のスレッドで描けるが、
文字はプロセスで 1 つのフォントのキャッシュ(フォントの実体・グリフのビットマップと輪郭の覚え)と、FreeType の Face・
HarfBuzz の文字の並べ方を使う。これらは同時に複数のスレッドから使えない。

## 検討した選択肢

- 選択肢A: フォントの処理全体を 1 つのロック(再帰できる mutex)で守る。
- 選択肢B: スレッドごとにフォントのキャッシュを持つ。ロックは要らないが、フォントのファイルを開く・グリフを作る手間と
  記憶がスレッドの数だけ要る。
- 選択肢C: フォントの実体ごとに細かくロックする。並列に描けるが、作りが複雑になり、誤りやすい。

## 決定

**選択肢A を選ぶ。**

- `detail::font_mutex()`(再帰できる mutex)で、文字のレイアウトを作る処理(TextLayout の構築。HarfBuzz で並べ、
  フォールバックのフォントを探す)・フォントの実体を開く処理・グリフのビットマップと輪郭を作る処理を守る。
- **作ったグリフは消さず、std::map の節点は追加しても動かないので、受け取った参照はロックの外で読む。** 画素を合成する処理
  (描く処理の大半)はロックの外で行うので、並列に描ける。待つのは、新しい文字を並べる・初めてのグリフを作るときだけ。
- これで、別のスレッドで次ができる: Bitmap とその Canvas(図形・画像・文字・変換・レイヤー)、TextLayout の構築、Image の読み込み。
- 引き続き、別のスレッドから触ってはいけないもの: ウィジェット・Object・プロパティ・Application(テーマの色を含む。
  色はメインスレッドで決めて渡す)。

## 確かめたこと

- 4 つのスレッドで大きさの違う文字を同時に何度も描き、メインスレッドで描いた結果と画素が一致すること(テスト)。
- WSL で ThreadSanitizer を有効にしてすべてのテストを実行し、このライブラリのコードのデータ競合が報告されないこと
  (報告は、終了時の SDL が使う libdbus の内部のロックの順序の 1 件だけ)。

## 影響

- 多くのスレッドが同時に新しい文字を並べると、ロックを待つ。文字のレイアウト(TextLayout)を作っておいて使い回せば待たない。
