# 0060. Canvas を仮想関数を持たない具体的なクラスにし、描画先を内部に隠す

- 状態: 承認
- 日付: 2026-10-13

## 背景

Canvas は、描く関数がすべて純粋仮想関数の抽象クラスで、内部の RasterCanvas(plutovg)がそれを実装していた
([ADR 0032](0032-canvas-api.md))。仮想関数の表は ABI の一部なので、描く関数(グラデーションの種類・文字の描き方など)を 1 つ
足すたびに ABI が変わる([ADR 0057](0057-compatibility-abi-and-c-layer.md))。描く関数は今後も増える見込みが高い。
一方、利用者が Canvas を派生させる使い方は無い(Canvas はライブラリが作って paint に渡す)。

## 検討した選択肢

- 選択肢A: 今のまま。描く関数を足すたびに SONAME を上げる。
- 選択肢B: 公開の Canvas を仮想関数を持たない具体的なクラスにし、描く関数は内部の描画先へ処理を渡すだけにする。描画先の仮想関数は
  公開の ABI に含まれないので、後から足しても ABI は変わらない。呼び出しが 1 段増えるが、描画の重さに比べて無視できる。

## 決定

**選択肢B を採る。**

- 公開の Canvas は、描く関数(状態・基本の描画・手軽な描画)を仮想でない関数として持ち、描画先へのポインタ 1 つだけを持つ。
  コンストラクタは private で、ライブラリの中から窓口(`detail::ImplAccess<Canvas>::create`)で作る。コピーできない。
- 描画先は `Canvas::Impl`(`src/graphics/canvas_impl.hpp`。今までの純粋仮想関数をそのまま持つ抽象クラス)。RasterCanvas がこれを
  継ぎ、自分に描く公開の Canvas を `api()` で渡す(窓・Bitmap の canvas())。
- 描画先の差し替え(将来の GPU など)は、これまでどおりライブラリの中でできる。

## 影響

- 利用者のコードは変わらない(Canvas& を受け取って描くだけなので)。Canvas を派生させていたコードは無い前提。
- リファレンスの部品の画像は、前と画素まで同じ(暦の「今日」の印を除く)。
