# 0016. プロパティどうしを結びつける汎用の仕組みを入れ、Variable はその特別な場合とする

- 状態: 承認
- 日付: 2026-10-04

## 背景

cpp_tk の `StringVar` 等(Tk の変数)のような、値を観察できる変数を入れたい。目的は次のすべて。

1. 1 つの値を複数のウィジェットで共有する(入力欄で書き換えるとラベルも変わる)。
2. ラジオボタンのグループを 1 つの変数で表す。
3. ウィジェットを経由せず、データの側から値を読み書きし、変更に反応する。

## 検討した選択肢

- 選択肢A: Tk の `-textvariable` のように、結びつけられるウィジェットにだけ専用のプロパティを用意する(`edit->text_variable = name`)。
  走り出しは楽だが、ウィジェットごとに専用のプロパティと処理が増える。
- 選択肢B: 任意のプロパティどうしを結びつける汎用の仕組みにする(`tokotachi::bind(edit->text, name->value)`)。
  プロパティの変更を知らせる仕組みが要るが、一度作れば、ウィジェットごとに必要なのは「変わったプロパティを知らせる」ことだけになる。

統一的な仕組みの方が全体の実装の手間が下がると考え、選択肢B を試作した。

## 決定

### 変更の通知

- プロパティは、所有者とプロパティ(`Property`・`ReadOnlyProperty`)のアドレスの組で識別する。
- **プロパティの値が変わったときだけ**、所有者が `notify_changed(property)` で知らせる(内部では `detail::property_changed`)。
  - ライブラリの中のプロパティは、書き込みの関数の前後で値を比べ、変わっていれば自動で知らせる(`property_impl.hpp` のマクロ)。
    この自動の通知を使う書き込みの関数は、利用者のハンドラを呼ばない(ハンドラがオブジェクトを破棄すると、後で値を読めないため)。
    ハンドラを呼ぶ書き込みの関数は、ハンドラより先に自分で知らせる。
  - **一緒に変わる別のプロパティは、書き込みの関数が知らせる**(`x` を変えると `bounds` も、LineEdit の `text` を変えると `cursor_position`・
    `selected_text` も変わる)。知らせないと、一緒に変わった方に結んだ相手が古いままになる。
  - **書き込みの関数を通らない変更**(利用者の操作による入力・キャレットの移動・フォーカスの移動、ウィンドウの大きさの変更、
    1 回だけのタイマーの停止)は、ウィジェットが自分で知らせる。
  - 結びつけた相手へ伝えてから、ウィジェットのハンドラ(`on_change` 等)を呼ぶ(ハンドラの中で相手の値がそろっているように)。
  - 利用者が自分で書いたプロパティは、書き込みの関数で `notify_changed` を呼ぶ。呼ばなければ結びつけても伝わらない。

### 結びつき

- `tokotachi::bind(target, source)`: 同じ型(`==` で比べられる型)のプロパティを双方向に結び、結んだ時点で target を source の値にする。
- **結びつきは、値が変わったときだけ相手へ伝える**。相手がすでに同じ値なら書き込まない(同じ値を書き込むと、LineEdit のキャレットが
  末尾へ動くなどの副作用があるため)。
  source が `ReadOnlyProperty` なら source から target への一方向。
- `tokotachi::unbind(a, b)` で 1 組、`tokotachi::unbind(property)` でそのプロパティの結びつきをすべて外す。どちらかのオブジェクトが破棄されると、
  その結びつきは自動で外れる。同じ組を 2 度結んでも 1 つにする。
- 結びつきは内部の一覧で管理し、利用者には見せない。メインスレッドだけで扱う。
- **循環の防止**: 結びつきは「伝えている最中」の印を持ち、伝えた先から戻ってきた通知を通さない。結びつきが輪になっていても止まる。

### Variable

- `tokotachi::Variable<T>` は「値のプロパティ `value` を 1 つ持つ Object」で、結びつきの特別な場合として扱う(Variable 専用の仕組みは無い)。
  別名 `StringVariable`・`IntVariable`・`BoolVariable`・`DoubleVariable` を用意する。
- ハンドラを 2 つに分けて提供する(どちらも単一のハンドラ。[ADR 0013](0013-api-style-properties-and-handlers.md))。
  - `on_set`: `value` が設定されるたびに呼ぶ(同じ値の代入でも)。内部の処理で明示的に代入したのにハンドラが呼ばれない、
    ということが無いようにするため。
  - `on_change`: `value` が変わったときに呼ぶ(結びつけた相手から伝わったときも含む)。`on_set` の後に呼ぶ。
- 所有者を持てる([ADR 0015](0015-object-ownership.md))。

### ウィジェットのハンドラ

- ウィジェットの `on_change`(LineEdit の text、CheckBox の checked、RadioButton の checked)は、名前どおり値が変わったときだけ呼ぶ
  (利用者の操作・代入のどちらでも)。ウィジェットに `on_set` が要る場面が出てきたら加える。
- 結びつけた相手へ伝えてから、ハンドラを呼ぶ。

### 検討した通知の決まり

- (a) 設定のたびに知らせる: 結びつきが輪になっていると同じ値の通知が重複する(下記)。
- (b) 値が変わったときだけ知らせる: 内部の処理で明示的に代入したのにハンドラが呼ばれないことが、利用者の期待と違う可能性がある。
- (c) `on_set` と `on_change` に分ける: 両方の要求を満たす。**これを採り、結びつきは (b) にした。**

## 試作で分かったこと

- 3 つの目的は、型の一致したプロパティの結びつきだけで満たせた。ラジオボタンのグループは、各ボタンに「自分の値」(`value`)と
  「グループで選ばれている値」(`group_value`)を持たせ、`group_value` を共有の `IntVariable` に結べばよい(型の変換は要らない)。
  押したボタンだけが選ばれ、変数から選ぶこともできることを、テストとサンプル(examples/hello)で確かめた。
- 最初の試作((a) 設定のたびに伝える)では、a・b・c を輪に結んで a に代入すると、`on_change` が a で 3 回、b・c で 2 回呼ばれた
  (どの結びつきも 1 回の変更で 2 度は通らないが、輪を逆向きに回る経路でも伝わるため)。結びつきを「値が変わったときだけ」にしてからは
  1 回ずつになった(テストで確かめている)。
- 一緒に変わるプロパティを知らせ忘れるのが、最も起きやすい不具合になる。ウィジェットごとに「操作したら結んだ変数が変わる」ことを
  テストで確かめる。
- 読み取り専用のプロパティのうち、`showing`・`effectively_enabled` 等の祖先の状態から決まるものは、まだ変化を知らせない。

## 影響

- `Property::operator=` 自体は通知しない(通知は書き込みの関数の側にある)。プロキシは状態を持たないままで、大きさも変わらない。
- 書き込みの関数の前後で値を比べるため、自動の通知を使うプロパティの値の型は `==` で比べられる必要があり、代入のたびに値を 2 回読む。
- 結びつきが 1 つも無いときの通知の費用は、一覧が空かを見るだけ。
