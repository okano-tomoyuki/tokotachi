# 0053. デザイナーが埋め込む画像は別のソースに書き、大きい画像は警告する

- 状態: 承認
- 日付: 2026-10-12

## 背景

デザイナーは、定義ファイルが参照する画像のファイルの中身を、生成するウィンドウのソースに `unsigned char` の配列として埋め込んでいた
(dsl-spec.md Q4。実行するときに画像のファイルを探さなくてよいように)。アイコンは数 KB なので問題はなかったが、ImageBox(docs/adr/0048)で
写真のような大きい画像も参照できるようになった。1 バイトを `0xAB, ` の 6 文字ほどで書くので、1 MB の画像でソースは 6 MB ほどになる。
ウィンドウのソースが読みにくくなり、ハンドラを直すたびに配列もコンパイルし直す。大きさの制限も、知らせる仕組みも無かった。

## 検討した選択肢

1. 大きい画像を警告するだけ。
2. 配列を別のファイルに書く: ウィンドウのソースから include するファイル(`.inc`)/ 別の翻訳単位のソース(`.cpp`)。
3. 埋め込まずに、実行するときにファイルから読むこともできるようにする。

## 決定

1 と 2(別の翻訳単位)を組み合わせる。3 は大きい画像を扱う要望が出るまで行わない(埋め込みで「生成したコードだけで動く」性質を保つ)。

- 画像を参照するウィンドウは、ソースと同じフォルダに `<定義ファイルの名前>_images.cpp` を生成する。ファイル全体を 1 つの区間にし、
  生成し直すと上書きする。配列と大きさ(`tokotachi_image_<パス>`・`tokotachi_image_<パス>_size`)は、ウィンドウと同じ名前空間の中の
  `tokotachi_images_<クラス名>` の名前空間に置く(ウィンドウごとに分け、同じ画像の名前が重ならないように)。別の翻訳単位から使うので、
  定義の前に `extern` で宣言して外部結合にする。
- ウィンドウのソースは、区間 `tokotachi_setup_ui` の先頭で同じものを `extern` で宣言し、`load_from_data(配列, 大きさ)` で読む
  (`sizeof` は使えない)。`.inc` を include する方法は、ビルドの設定を変えずに済むが、ハンドラを直すたびに配列もコンパイルし直すので選ばない。
- プロジェクトに属するウィンドウは、CMakeLists.txt のソースの一覧(区間 `tokotachi_sources`)に画像のソースを入れる。
  プロジェクトに属さないウィンドウは、画像のソースを作ったときに、ビルドに加えるよう知らせる(コード生成の警告)。
- 画像を参照しなくなったら、画像のソースは書かない。前に書いたものは消さず(利用者のビルドが壊れないように)、使われていないことを知らせる。
- 256 KB(`LARGE_IMAGE_BYTES`)を超える画像のファイルは、拡張が問題パネルに警告を出す(`large-image`)。コードの生成は止めない。
- 大きい画像でも生成・描画できるようにする(16 MB の PNG で確かめた)。
  - 区間の置き換えは、行の配列を引数に展開しない(`splice(i, n, ...lines)` は数十万行でスタックがあふれた)。
    バイトの文字は表から引き、区間のハッシュは空白を除いた写しを作らずに計算する(4 MB の画像で、生成 1 回が約 2.7 秒から 0.8 秒に)。
  - キャンバスへの描画の要求は、wasm のヒープに置いて渡す(`ccall` の文字列の引数は wasm のスタック(64 KB)に置かれ、
    画像を含む大きい要求で `memory access out of bounds` になった)。

## 影響

- 画像を参照する既存のウィンドウは、生成し直すと画像のソースが増える。プロジェクトに属さなければ、利用者がビルドに加える必要がある。
- よく使うアイコンは、ライブラリに線画のパスとして組み込む予定(Lucide から選ぶ)。そうすれば、アイコンは埋め込まずに済む。
