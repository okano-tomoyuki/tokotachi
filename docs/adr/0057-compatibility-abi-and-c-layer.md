# 0057. 1.0 からの互換の約束と pimpl・ABI・公開するシンボル・将来の C の層の方針

- 状態: 承認
- 日付: 2026-10-12

## 背景

1.0 を出すと、利用者のコードを壊す変更は大きい版(2.0)まで入れられなくなる。その前に、何をどこまで守るかを決める。

- **非公開のメンバが見えている**: 公開のヘッダは、クラスの非公開のデータ(`ColorDialog` の `hue_` など)・非公開のメンバ関数・
  `detail` のクラスの前方宣言と `friend` をそのまま持つ。言語の上では使えないが、利用者に見え、ヘッダを書き換えれば使えてしまう
  (論理的に非公開なだけで、物理的には非公開でない)。中身を少し変えるだけで、利用者のコードの作り直しも要る。
- **ABI**: [ADR 0037](0037-distribution.md) では、SONAME を 0.x の間は `0.<minor>`、1.0 からは大きい版にするとした。ところが非公開の
  メンバを 1 つ足すだけで ABI が変わる。さらに、プロパティ(`Property<T>`。1 つ 24 バイト)とハンドラ(`std::function`。1 つ 32 バイト)は
  **公開のメンバ変数**([ADR 0013](0013-api-style-properties-and-handlers.md))なので、中身を隠しても、プロパティ・ハンドラ・仮想関数を
  足せばクラスの大きさとメンバの位置が変わる(`Window window(...)` とスタックに置くコード、Window・PaintBox を派生させたコードが壊れる)。
  C++11 では空のメンバも 1 バイト以上の大きさを持つので、プロパティの書き方を保ったまま大きさを変えない方法は無い。
  Qt は、公開のクラスにはポインタ 1 つ(d ポインタ)だけを持たせ、値を関数で読み書きすることで、大きい版の中の ABI を守っている。
- **公開するシンボル**: ADR 0037 では、このライブラリのシンボルをすべて公開し、印(`TOKOTACHI_API`)で絞るのは 1.0 の前に検討するとした。
  今は `detail` の内部のクラスも公開されていて、利用者が使えてしまう(使われると内部を変えられなくなる)。
- **ほかの言語**: 別のプロジェクト Bethany(Lazarus の LCL を C の関数の DLL にし、C++・Python から使う)では、C の関数の決まり
  (中身を見せないハンドル・UTF-8・Get/Set・SetOnXxx・破棄の通知・例外を境界でとめる)で複数の言語に対応している。
  Tokotachi も、いずれほかの言語から使えるようにしたい。ほかの言語から使うときに長く守るべき境界は、C++ の ABI ではなく C の関数になる。

## 検討した選択肢

- 選択肢A: pimpl にし、大きい版の中では既存のクラスに公開のメンバ(プロパティ・ハンドラ・仮想関数)を足さない。
  - C++ の ABI を大きい版の中で守れる(Qt と同じ約束)。
  - 小さい版で機能を足すときは、関数か新しいクラスにするしかなく、プロパティを中心にした書き方と合わない。
- 選択肢B: pimpl にし、**ABI が変わったときだけ** SONAME を上げる。変わったかどうかは CI で機械的に確かめる。
  - 中身の変更は ABI に響かなくなり、ABI が変わるのは公開のメンバを足した小さい版だけになる。うっかり壊すことも CI が防ぐ。
  - 長く守る ABI は、将来の C の層で提供する。
- 選択肢C: pimpl にせず、ABI は小さい版ごとに変わるものとする。
  - 作業は少ないが、非公開のメンバが物理的に見えたままで、中身の変更のたびに ABI が変わる。
- 選択肢D: 何も約束しない。
  - 1.0 の意味が無くなる。
- (プロパティを `text()` のような関数にする案は、ADR 0013 の書き方を変えるので採らない。クラスの末尾に予備の領域を置いて後で
  置き換える案は、`std::function` の大きさが環境で違うなど無理が多いので採らない。)

## 決定

**選択肢B を採る。**

### pimpl(物理的に非公開にする)

- Object から派生する公開のクラスは、非公開のデータと非公開のメンバ関数を、入れ子の実装のクラス `Impl` に移す。公開のヘッダの
  非公開の部分には、`class Impl;` と、それを指すポインタ `Impl* d_;` だけを残す(`detail` の前方宣言も friend も要らない)。
  入れ子のクラスは外側のクラスのメンバと同じ扱いなので、`Button::Impl` は Button の private のメンバに触れ、公開のクラスへのポインタ
  `q` を通して基底の protected のメンバも呼べる。
- 実装のクラスは、クラスの階層の段ごとに持つ(`Widget::Impl` と `Button::Impl` は別の型)。段ごとに確保が増えるが、利用者が派生させた
  クラスに影響せず、段ごとに独立して変えられる。
- ほかのクラスの実装のコードから届くクラス(Widget・Layout など)だけ、ヘッダで内部の窓口を friend にする
  (`template <typename> friend struct detail::ImplAccess;`。窓口の前方宣言は property.hpp に 1 つ)。窓口は
  `detail::ImplAccess<Layout>::of(layout)` で実装のクラスを返す。protected のメンバを呼ぶなどの関数が要るクラスは窓口を特殊化し、
  今の `detail::LayoutAccess` などは、その特殊化の別名(`typedef ImplAccess<Layout> LayoutAccess;`)にする。部品ごとの
  `friend class detail::ColorPlane` などはヘッダから無くす。仕組みは `src/core/impl.hpp`(`TOKOTACHI_IMPL`・`TOKOTACHI_IMPL_ACCESS`・
  `TOKOTACHI_IMPL_PROPERTY_...`)。
- プロパティの読み書きの関数(`TOKOTACHI_PROPERTY_MEMBER` がつなぐもの)は、ヘッダの非公開のメンバ関数ではなく、ソースの中の関数にする。
- ヘッダに残すもの: 公開のメンバ(プロパティ・ハンドラ・関数)、利用者が派生して上書きする `protected` の仮想関数(`paint` など)、
  インラインで書くと速さが要るもの(値の型)。値の型(Point・Color・Rect など)とテンプレート(Property・WeakRef など)は pimpl にしない。

### 互換の約束(1.0 から)

| 対象 | 守る範囲 | 壊す変更を入れられるとき |
|---|---|---|
| C++ の API(ソース) | 大きい版の中(1.x を上げても、利用者のコードはそのままコンパイルできる) | 2.0 |
| C++ の ABI | 公開のメンバ(プロパティ・ハンドラ・仮想関数)・公開の値の型を変えない限り守る。変えた小さい版で SONAME を上げる | 小さい版 |
| 将来の C の層の ABI | 大きい版の中 | 2.0 |
| デザイナーの定義ファイル(`format_version`) | 古い形式を読み、新しい形式に移す | 移し替えを用意すれば、いつでも形式を上げられる |
| 生成するコードの印(region)と、生成したコードが使う API | デザイナーの大きい版の中 | デザイナーの大きい版 |

- **SONAME**: `libtokotachi.so.<major>.<ABI を最後に変えた小さい版>`。1.0 は `libtokotachi.so.1.0` で、1.1・1.2 が ABI を変えなければ
  そのまま、1.3 で変えたら `libtokotachi.so.1.3` にする(どの版の ABI かが名前で分かる)。Windows の DLL は今のとおり版を名前に入れず、
  exe の隣に置いて使う。
- **ABI の見張り**: 版を出すときに、Linux の共有ライブラリの ABI の記述を libabigail の `abidw` で作ってリポジトリに置く。CI は
  `abidiff` で今のビルドと比べ、SONAME を上げずに ABI が変わっていれば失敗にする。
- **CMake のパッケージの版の確かめ**: 1.0 からは、大きい版が同じで、求める版以上ならよいとする(ソースの互換に合わせる)。
- **非推奨**: すぐに消さず、`TOKOTACHI_DEPRECATED("代わりの名前")`(GCC の `__attribute__((deprecated))`。C++11 には `[[deprecated]]` が
  無い)を付けて警告を出し、次の大きい版で消す。リファレンスには `@deprecated` を書く。
- **ソースの互換に含めないもの**: `detail` 名前空間の中、`@internal` と書いたもの、テストのための入口。

### 公開するシンボル

- 公開のクラス・関数に `TOKOTACHI_API` を付け、それ以外は公開しない(Linux は `-fvisibility=hidden`・`-fvisibility-inlines-hidden`、
  MinGW は自動の公開をやめて、共有ライブラリをビルドするときだけ `__declspec(dllexport)`)。利用する側では Windows の印は空にし、
  MinGW の自動の読み込み(auto-import。今までと同じ)に任せる。`dllimport` を付けないので、利用する側は共有か静的かを知らせずに済む
  (CMake のパッケージ・pkg-config に定義を足さない)。印は `include/tokotachi/core/export.hpp` で定める。
- 公開のヘッダのテンプレート・インラインの関数から呼ぶ `detail` の関数(`detail::add_binding` など)にも付ける(付けないと利用者の
  コードがリンクできない)。
- テストは、今と同じく内部のライブラリ(依存ライブラリごと静的にリンクしたもの)を使うので、印の影響を受けない。

### 例外

- ライブラリは例外を投げない(メモリが足りないときの `std::bad_alloc` を除く。今のソースにも `throw` は無い)。
- 利用者のハンドラは、例外をハンドラの外へ出してはならない。将来の C の層は、コールバックの例外を境界の手前で捕まえる。

### 将来の C の層(1.0 には入れない)

- C++ の API の上に、`extern "C"` の関数の薄い層を重ねる。C++ がライブラリの土台で、C の層はほかの言語のための出入り口にすぎない
  (Bethany とは向きが逆で、既存の GUI の層を薄く包むものではない)。
- 決まりは Bethany の DLL の関数の決まりに合わせる: 中身を見せないハンドル、UTF-8 の文字列(返す文字列はスレッドごとのバッファ)、
  プロパティは Get/Set の組、イベントは `set_on_xxx(obj, cb, data)`(最後に登録したものだけ。Tokotachi のハンドラ 1 つの決まりと同じ)、
  破棄の通知、例外を境界でとめる。
- 関数の一覧は手で書かず、デザイナーのカタログ(`catalog.json`。ヘッダから取り出した部品・プロパティ・型・イベント)から生成する。
  ほかの言語の層(最初は Python)も同じところから生成する。
- 1.0 の後、Python で試作して形を固める。派生して書くもの(ItemModel・自作の部品)、`Variable` と結びつけ、Task・`post` は、
  試作の中で決める。

### 1.0 に入れておく下地

- オブジェクトの破棄を外から知る仕組み(C の層が、ほかの言語の側の参照を無効にするために使う)。
  - 実装: `detail::add_destroy_observer`・`remove_destroy_observer`(`src/core/object_impl.hpp`。共有ライブラリから公開するが、公開の
    ヘッダには出さず、互換の約束にも含めない)。~Object の最初に、破棄される順に `fn(object, data)` を呼ぶ。そのときには派生クラスの
    部分はもう破棄されているので、受け取った側はポインタの同一性(ハンドルを無効にする)にだけ使う。C++ の利用者は WeakRef で
    破棄されたかを確かめられるので、公開の `on_destroy` は足さない(すべての Object の大きさが変わるため。要望が出たら、ABI を
    変える版で足す)。

## 影響

- あわせて、ライブラリのテストを CI(`.github/workflows/library.yml`。Windows の mingw64、Linux の x86_64・aarch64)で動かすようにした。
  以下の作業は、この CI で確かめながら進める。
- pimpl の作業: `private:` を持つ公開のヘッダ(59 個)のうち、Object から派生するクラスを、ディレクトリごとに分けて移す。
  オブジェクトごとに確保が増えるが、GUI の部品の数では問題にならない。内部の窓口(`detail::WidgetAccess` など)と、
  テストが実装に触れるところは、窓口(`detail::ImplAccess`)を通すように直す。
- `TOKOTACHI_API` を公開のヘッダ全体に付ける作業と、公開しなくなったシンボルを使っていないことの確かめ(サンプル・生成したプロジェクト・
  インストールしたものを別のプロジェクトから使う確かめ)が要る。
- 1.0 の後に既存のクラスへプロパティ・ハンドラ・仮想関数を足すときは、その小さい版で SONAME を上げる。ソースの互換を壊す変更は、
  非推奨を経て次の大きい版で入れる。
- C の層を作るまでは、ほかの言語からは使えない。
