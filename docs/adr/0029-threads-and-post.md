# 0029. GUI はメインスレッドだけで触り、別のスレッドからは post で頼む。スレッドのクラスは作らず、終わりのある仕事は Task で表す

- 状態: 承認
- 日付: 2026-10-04

## 背景

重い処理(ファイルの読み込み・計算・通信)を別のスレッドで行い、結果を画面に出したい。決めること:

- どのスレッドから GUI(ウィジェット・Object・プロパティ)に触ってよいか。
- 別のスレッドからメインスレッドへ処理を頼む方法と、頼んだ処理が呼ばれる前に相手が破棄された場合の扱い。
- Qt の QThread・Delphi の TThread のような、スレッドのクラスを用意するか。

## 検討した選択肢

- 選択肢A: スレッドのクラス(QThread・TThread の形)と、フリー関数による呼び出しの両方を用意する。
- 選択肢B: フリー関数による呼び出し(post)を土台にし、スレッドは C++11 の `std::thread` に任せる。
  終わりのある仕事のために、後で型付きの結果を返す Task を用意する。
- 選択肢C: GUI の全体をスレッドから安全にする(ロックを持つ)。速さを失い、SDL3 のウィンドウ・イベントはメインスレッドでしか
  扱えないので、結局は頼む仕組みも要る。

## 決定

**選択肢B を選ぶ。**

- **ウィジェット・Object・プロパティ・結びつけは、メインスレッド(Application を作ったスレッド)からだけ触る。** ロックは持たない。
  `gui::is_main_thread()` で確かめられる。
- `gui::post(fn)`: どのスレッドからでも呼べる。`fn` をメインスレッドで、イベントの処理の中で、頼んだ順に呼ぶ
  (SDL のユーザーイベントで送るので、待機中のイベントループも起きる)。Application が無い・終わった後は頼まずに false を返す。
  Application が終わるまでに呼ばれなかったものは、呼ばずに捨てる。
- `gui::WeakRef<T>`: Object への弱い参照。Object が生きているかの目印(`shared_ptr` で共有する)を見る。
  **作るのと `get()` はメインスレッドで行い、別のスレッドへはコピーで渡す。** 別のスレッドから生のポインタで頼むと、
  その時点で破棄されているか(同じアドレスに別の Object が作られているか)を安全に確かめられないため。
- `gui::post(ref, fn)`: 呼ぶ時点で Object が残っていれば `fn(ポインタ)` を呼び、破棄されていれば呼ばない。
- **終わるまで待つ呼び出し(TThread の Synchronize、Qt の BlockingQueuedConnection に当たるもの)は用意しない。**
  メインスレッドが別のスレッドの終わりを待っている間に、その別のスレッドがメインスレッドを待つと、デッドロックになるため。
- スレッドのクラスは作らない。常駐するスレッド(通信の受信・ゲームのループなど)は `std::thread` で作り、結果を post で返す。
  C++11 に `std::thread`・`std::mutex`・`std::atomic` があり、包むだけのクラスの価値は小さい。QThread は所属のスレッドの扱いを、
  TThread は Synchronize の待ちを誤りやすい。
- ライブラリは `Threads::Threads` を公開の依存にする(利用者がそのまま `std::thread` を使えるように)。

### Task(終わりのある仕事)

- `Task<T>`(と `Task<void>`)はメインスレッドの Object。`start(関数)` で仕事を別のスレッドで始める(実行ごとにスレッドを作る)。
  動いている間の `start` は false を返す。
- 仕事の関数には `TaskContext&` だけを渡す。`cancel_requested()`・`report_progress(値)` はスレッドをまたいで安全。
  ウィジェットに触れる手段を渡さないことで、誤って別のスレッドから触ることを防ぐ。
- 進み具合は間引いて届ける: 届ける途中に何度知らせても、`on_progress` は届いたときの最後の値で 1 回だけ呼ぶ。
- **結果は `std::future` を見せず、`on_finish`(メインスレッド)の中で型付きの `result` として読む。** GUI では future を待つ・
  調べ続けることになるため。T はコピーと既定の構築ができること。
- 仕事が投げた例外は受け取り、`error`(メッセージ)にする。取り消しを頼んだ後に終わったら `cancelled` が true。どちらでも `on_finish` を呼ぶ。
- `cancel()` は頼むだけで、仕事が戻るまで待たない。Task(または持ち主)が破棄されたら取り消しを頼み、結果・進み具合は届けない
  (WeakRef で止める)。実行ごとに状態を分けるので、取り消した直後に始め直しても、前の実行の結果は混ざらない。

## 影響

- メインスレッド以外からウィジェットに触る誤りは、今は検出しない(デバッグ用の確かめは後で検討する)。
- Object は WeakRef が作られたときだけ、生きているかの目印(shared_ptr 1 つ)を持つ。
