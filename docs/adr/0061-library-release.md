# 0061. ライブラリの版の出し方(タグ・変更履歴・パッケージ・利用者のプロジェクトでの確かめ)

- 状態: 承認
- 日付: 2026-10-13

## 背景

[ADR 0037](0037-distribution.md) で配る形(共有・静的、CMake のパッケージ・pkg-config・ソースからの組み込み)を決め、手で確かめた。
しかし、ライブラリの版をどう出すかは決めておらず、タグも付けていなかった。1.0 の前に 0.2.0 を出して利用者に試してもらうにあたり、
出し方を決め、配る形が壊れていないことを毎回機械で確かめたい。

## 検討した選択肢

- 配るもの: ソースとタグだけ(利用者がビルドする)/ビルドしたパッケージも添える。依存ライブラリのビルドに数分かかり、MinGW では
  環境をそろえる手間もあるので、パッケージも添える。
- Release の作り方: CI がそのまま公開する/下書きを作り人が公開する。出したものは取り消しにくいので、下書きにする。
- 配る形の確かめ: リリースのときだけ/毎回の CI。シンボルを絞るなど配る形に効く変更はふだんの開発で入るので、毎回確かめる。

## 決定

### 版とタグ

- 版は `include/tokotachi/core/version.hpp` だけで管理する(ADR 0037)。互換の約束と SONAME は [ADR 0057](0057-compatibility-abi-and-c-layer.md)。
- ライブラリのタグは `v<版>`(例: `v0.2.0`)。デザイナーのタグ `designer-v<版>` とは別に付ける。
- 変更履歴はリポジトリの根の `CHANGELOG.md` に、版ごとの節(`## <版>`)で書く。利用者のコードの修正が要る変更は、分けて書く。

### 出す手順

1. `version.hpp` の版を上げ、`CHANGELOG.md` にその版の節を書き、デザイナーのカタログを取り出し直す(`pnpm catalog:extract`。
   デザイナーが生成する `find_package` の版は、カタログを取り出したライブラリの版から決まる)。コミットし、CI が通るのを待つ。
2. `v<版>` のタグを付けて push する。
3. CI(`.github/workflows/library.yml`)が、タグと `version.hpp` の版が同じかを確かめ、パッケージを作り、`CHANGELOG.md` のその版の節を
   説明にした GitHub の Release の**下書き**を作る(0.x の間はプレリリースの印を付ける)。
4. 下書きの中身を確かめてから、GitHub の画面で公開する。

### パッケージ

- Linux(x86_64・aarch64。Ubuntu 24.04 でビルド)と Windows(MSYS2 の MINGW64)ごとに、共有ライブラリと静的ライブラリの
  インストールの結果をまとめる(`tokotachi-<版>-<プラットフォーム>-<shared|static>`。Windows は .zip、Linux は .tar.gz)。
  プラットフォームごとに SHA256 を添える。
- ビルドした環境(コミット・コンパイラ・glibc)を、パッケージの中の `BUILD_INFO.txt` に書く。C++ の ABI はコンパイラと標準ライブラリに
  依存するので、利用者は同じ系統の環境で使う(Linux は glibc・libstdc++ がビルドした環境以上、Windows は MSYS2 の MINGW64 の GCC)。
- MinGW のランタイムの DLL はパッケージに入れない(利用者のコンパイラのものを使う)。

### 利用者のプロジェクトでの確かめ(毎回の CI)

- CI は、タグの有無にかかわらず、共有ライブラリ・静的ライブラリのそれぞれをインストールし、`tests/install/` の利用者のプロジェクトを
  CMake のパッケージ(`find_package(tokotachi <版> EXACT)`)と pkg-config の両方でビルドして、画面なしで動かす。
- 利用者のプロジェクトは公開のヘッダだけを読み、公開のクラスから派生させて `paint` を上書きし、標準の見た目を描く関数・プロパティの
  結びつけ(ヘッダの中のテンプレート)・タイマー・イベントループを使い、実行時の版(`tokotachi::version()`)がヘッダの版と同じかを確かめる。
  公開するシンボルを絞ったこと([ADR 0057](0057-compatibility-abi-and-c-layer.md))で、利用者から使えなくなったものが無いかも、ここで分かる。

## 影響

- 0.2.0 が、最初にタグを付けて出す版になる(0.1.0 は付けなかった)。
- デザイナーが新しく作るプロジェクトの CMakeLists.txt は、カタログの版(0.2)を求める。0.1 のときに作ったプロジェクトの
  CMakeLists.txt はデザイナーが書き換えない(利用者のもの)ので、`find_package(tokotachi 0.1 REQUIRED)` を手で直す。
- ABI が変わったかを機械で確かめる仕組み(abidiff)は、1.0 を出すときに足す(ADR 0057)。
- Linux のディストリビューション・MSYS2 のパッケージは、引き続き後で対応する(ADR 0037)。
